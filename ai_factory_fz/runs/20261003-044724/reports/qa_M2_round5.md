## Bugs
### BUG-001 [major] Unexpected (non-HttpException) errors on catalog/health endpoints drop the contractually-required 'error' field from the 500 response (WI-005)
Steps: 1) No global exception filter is registered anywhere in server/src (only ValidationPipe's exceptionFactory handles 400s; NotFoundException/ServiceUnavailableException are plain HttpExceptions that Nest formats correctly). 2) For any other error thrown out of CatalogService (server/src/catalog/catalog.service.ts) or HealthService when prisma.*.findMany/count/findUnique/$queryRawUnsafe rejects with a generic Error (e.g. a dropped DB connection), Nest's built-in exception handling falls back to `{ statusCode: 500, message: 'Internal server error' }` with no 'error' property, because that fallback only applies to non-HttpException instances. 3) Reproduce deterministically with server/test/m2-error-shape.e2e-spec.ts, which overrides PrismaService with a stub whose methods reject with a generic Error, then calls GET /api/v1/categories, GET /api/v1/products, and GET /api/v1/products/00000000-0000-0000-0000-000000000000; the assertions on res.body.error fail for all three.
Expected: Per docs/openapi.yaml's ErrorResponse schema (required: [statusCode, error, message], additionalProperties: false, reused by the 500 ServerError response on /categories, /products and /products/{productId}) and the stated backend convention 'Errors return { statusCode, error, message } with correct HTTP codes', any 500 response must include a non-empty 'error' field alongside statusCode and message.
Actual: An unexpected Prisma/service error on any catalog endpoint returns `{ statusCode: 500, message: 'Internal server error' }` with no 'error' field at all, violating the documented contract and breaking any strict consumer (including a generated Dart ErrorResponse model) that requires 'error'.

### BUG-002 [minor] Environment validation accepts an empty DATABASE_URL instead of failing fast at startup (WI-005)
Steps: 1) Open server/src/config/environment.validation.ts: DATABASE_URL is decorated only with @IsString() (no @IsNotEmpty()/@MinLength(1)). 2) Call validateEnvironment({ DATABASE_URL: '', PORT: '3000' }) (see 'documents that an empty DATABASE_URL currently passes validation' in server/src/config/environment.validation.spec.ts): it resolves successfully instead of throwing, unlike a fully-missing DATABASE_URL which does throw.
Expected: Per the backend convention 'Config via environment variables validated at startup (@nestjs/config)', a structurally invalid DATABASE_URL (empty string) should fail validation immediately with a clear 'Environment validation failed' error, the same way a missing DATABASE_URL does.
Actual: An empty-string DATABASE_URL passes startup validation silently; the real failure only surfaces later and more opaquely when PrismaService.$connect() runs in onModuleInit, producing a generic Prisma connection error instead of a clear config-validation message.

### BUG-003 [minor] GET /api/v1/products/{productId} can return an undocumented 400 for a malformed UUID (only 200/404/500 are declared) (WI-005)
Steps: 1) In docs/openapi.yaml, the /products/{productId} GET operation's responses only declare '200', '404', and '500' - there is no '400' entry. 2) In server/src/catalog/catalog.controller.ts, getProductById uses @Param('productId', ParseUUIDPipe), which throws a 400 BadRequestException for any non-UUID path segment. 3) Exercised by 'GET /api/v1/products/{productId} with a malformed id returns 400, not 500' in server/test/m2-catalog-contract.e2e-spec.ts: GET /api/v1/products/not-a-uuid returns 400.
Expected: Per 'the OpenAPI document is the contract; the code follows it', every status code the implementation can actually return for an operation should be declared in docs/openapi.yaml, or the code should only return a documented code (e.g. map a malformed id to the documented 404 instead of an undocumented 400).
Actual: The endpoint returns HTTP 400 for a syntactically invalid productId, a status code not declared anywhere in the /products/{productId} operation's responses in docs/openapi.yaml, so a client built strictly from the contract (including a generated Dart client) has no typed model for this case.
