## Bugs
### BUG-001 [major] `npm test` deterministically fails unit tests in environment.validation.spec.ts with `TypeError: Reflect.getMetadata is not a function` because reflect-metadata is never imported where it's needed (WI-005)
Steps: 1) server/src/config/environment.validation.ts calls `plainToInstance(EnvironmentVariables, config, { enableImplicitConversion: true })`. 2) With enableImplicitConversion:true, class-transformer's TransformOperationExecutor (node_modules/class-transformer/cjs/TransformOperationExecutor.js, the `else if (this.options.enableImplicitConversion && this.transformationType === PLAIN_TO_CLASS)` branch) unconditionally calls `Reflect.getMetadata('design:type', targetType.prototype, propertyName)` with no feature-check guard. 3) `Reflect.getMetadata` only exists once the `reflect-metadata` package has been imported somewhere in the running module graph as a side effect; environment.validation.ts imports only class-transformer/class-validator and never imports 'reflect-metadata' itself. 4) In production the app only works by accident because main.ts's first import is `@nestjs/core`, which does `import 'reflect-metadata'` at its own index.js:7 (same for @nestjs/common), before ConfigModule.forRoot(validate: validateEnvironment) ever runs. 5) environment.validation.spec.ts imports environment.validation.ts directly and never imports @nestjs/core or @nestjs/common, so in vitest's isolated per-file module context Reflect.getMetadata is undefined when validateSync's plainToInstance call runs. 6) Prior QA (round 7, see reports/qa_M2_round7.md) ran `npm test` three times and reproduced '4 of 27 tests failed, all in src/config/environment.validation.spec.ts' every time; no commit has touched environment.validation.ts or added a reflect-metadata import since (git log confirms the file is unchanged since commit b3c2c0c, and the subsequent WI-006/WI-007 attempts this round were discarded), so this is still live in the current tree.
Expected: Per the backend convention 'Tests: Jest unit tests per service', `npm test` passes for every unit spec regardless of which other files run alongside it, and .github/workflows/server-ci.yml's 'Unit tests' step (`npm test`) is green.
Actual: Every run of `npm test` throws `TypeError: Reflect.getMetadata is not a function` inside environment.validation.spec.ts's calls to validateEnvironment(), failing 4 of that file's tests deterministically and leaving CI red on every push touching server/. Fix: add `import 'reflect-metadata';` as the first line of server/src/main.ts (or environment.validation.ts, or a vitest setupFiles entry) so the polyfill loads before any plainToInstance call with enableImplicitConversion.

### BUG-002 [minor] Environment validation accepts an empty-string DATABASE_URL instead of failing fast at startup (WI-005)
Steps: 1) Open server/src/config/environment.validation.ts: `DATABASE_URL` is decorated only with `@IsString()`, no `@IsNotEmpty()`/`@MinLength(1)`. 2) Call `validateEnvironment({ DATABASE_URL: '', PORT: '3000' })` (see the existing test 'documents that an empty DATABASE_URL currently passes validation (should be rejected)' in environment.validation.spec.ts, which asserts `result.DATABASE_URL === ''` rather than a thrown error). 3) Code inspection confirms the gap is unchanged from the prior QA round (no diff on this file since commit b3c2c0c).
Expected: Per the backend convention 'Config via environment variables validated at startup (@nestjs/config)', a structurally invalid DATABASE_URL (empty string) fails validation immediately with a clear 'Environment validation failed' error, the same way a missing DATABASE_URL does.
Actual: An empty-string DATABASE_URL passes startup validation silently; the real failure only surfaces later, more opaquely, when PrismaService.$connect() runs in onModuleInit, producing a generic Prisma connection error instead of an actionable config-validation message.

### BUG-003 [minor] GET /api/v1/products/{productId} can return an undocumented 400 for a malformed UUID (only 200/404/500 are declared in the contract) (WI-005)
Steps: 1) docs/openapi.yaml lines 118-141: the /products/{productId} GET operation's `responses` only declare '200', '404', and '500' — there is no '400' entry. 2) server/src/catalog/catalog.controller.ts's getProductById uses `@Param('productId', ParseUUIDPipe)`, which throws a 400 BadRequestException for any non-UUID path segment. 3) Reproduce: `GET /api/v1/products/not-a-uuid` -> 400 (exercised by 'GET /api/v1/products/{productId} with a malformed id returns 400, not 500' in server/test/m2-catalog-contract.e2e-spec.ts, which asserts the current, undocumented behavior rather than failing on it).
Expected: Per 'the OpenAPI document is the contract; the code follows it', every status code the implementation can actually return for an operation is declared in docs/openapi.yaml — or the code maps a malformed id onto one of the already-documented codes (e.g. 404) instead of an undocumented 400.
Actual: The endpoint returns HTTP 400 for a syntactically invalid productId, a status code not declared anywhere in this operation's documented responses, so a strict client built only from the contract (including any future generated Dart client) has no typed model for this case.
