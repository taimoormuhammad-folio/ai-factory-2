## Bugs
### BUG-001 [major] `npm test` deterministically fails 4/27 unit tests: environment.validation.spec.ts throws 'Reflect.getMetadata is not a function' (WI-005)
Steps: 1) server/src/main.ts and server/src/config/environment.validation.ts never `import 'reflect-metadata'` directly; the app only gets that polyfill as a side effect of main.ts's first import being `@nestjs/core` (confirmed: node_modules/@nestjs/core/index.js:7 does `import 'reflect-metadata'`). 2) environment.validation.ts calls class-transformer's plainToInstance on a class decorated with class-validator decorators, which needs that global polyfill already loaded. 3) Vitest isolates each spec file into its own module context; src/config/environment.validation.spec.ts never imports @nestjs/core (directly or transitively), so Reflect.getMetadata is undefined there. 4) Reproduced 3/3 times by running `cd server; npm test` (vitest run): 'Test Files 1 failed | 5 passed (6)', 'Tests 4 failed | 23 passed (27)', all 4 failures in src/config/environment.validation.spec.ts with `TypeError: Reflect.getMetadata is not a function`. 5) .github/workflows/server-ci.yml's 'Unit tests' step runs exactly `npm test`, so CI is red on every push/PR touching server/.
Expected: Per the backend convention 'Tests: Jest unit tests per service', `npm test` should pass for all unit specs, including environment.validation.spec.ts, independent of which other test files happen to run alongside it.
Actual: `npm test` fails 4 of 27 tests every run with `TypeError: Reflect.getMetadata is not a function`, because environment.validation.ts (and/or the vitest config) never explicitly loads the `reflect-metadata` polyfill it depends on. The app itself still boots fine in production only because main.ts's first import happens to be `@nestjs/core`, which pulls in the polyfill before AppModule's ConfigModule.forRoot(validate: validateEnvironment) runs — but the test suite and CI pipeline are broken.

### BUG-002 [minor] Environment validation accepts an empty DATABASE_URL instead of failing fast at startup (WI-005)
Steps: 1) Open server/src/config/environment.validation.ts: `DATABASE_URL` is decorated only with `@IsString()` (no `@IsNotEmpty()`/`@MinLength(1)`). 2) The existing test 'documents that an empty DATABASE_URL currently passes validation (should be rejected)' in server/src/config/environment.validation.spec.ts calls `validateEnvironment({ DATABASE_URL: '', PORT: '3000' })` and expects `result.DATABASE_URL` to be `''` (i.e. it resolves instead of throwing) — confirmed still true by code inspection (this test currently can't execute due to BUG-001, but the source code shows the gap is unchanged since the prior QA round).
Expected: Per the backend convention 'Config via environment variables validated at startup (@nestjs/config)', a structurally invalid DATABASE_URL (empty string) should fail validation immediately with a clear 'Environment validation failed' error, the same way a missing DATABASE_URL does.
Actual: An empty-string DATABASE_URL passes startup validation silently; the real failure only surfaces later and more opaquely when PrismaService.$connect() runs in onModuleInit, producing a generic Prisma connection error instead of a clear config-validation message.

### BUG-003 [minor] GET /api/v1/products/{productId} can return an undocumented 400 for a malformed UUID (only 200/404/500 are declared) (WI-005)
Steps: 1) In docs/openapi.yaml lines 118-141, the /products/{productId} GET operation's responses only declare '200', '404', and '500' — there is no '400' entry. 2) In server/src/catalog/catalog.controller.ts, `getProductById` uses `@Param('productId', ParseUUIDPipe)`, which throws a 400 BadRequestException for any non-UUID path segment. 3) Exercised by 'GET /api/v1/products/{productId} with a malformed id returns 400, not 500' in server/test/m2-catalog-contract.e2e-spec.ts: `GET /api/v1/products/not-a-uuid` returns 400 (test code confirms this is the asserted/expected behavior, not a documented one).
Expected: Per 'the OpenAPI document is the contract; the code follows it', every status code the implementation can actually return for an operation should be declared in docs/openapi.yaml, or the code should only return a documented code (e.g. map a malformed id to the documented 404 instead of an undocumented 400).
Actual: The endpoint returns HTTP 400 for a syntactically invalid productId, a status code not declared anywhere in the /products/{productId} operation's responses in docs/openapi.yaml, so a strict client built only from the contract (including a generated Dart client) has no typed model for this case.
