### BUG-003 [major] Build pipeline can mark a work item 'done' with commit=null, silently losing all claimed work (WI-005)
Steps: Inspect state.json build.work_items['WI-005']: {"status": "done", "attempts": 1, ..., "commit": null}. Compare to WI-006/WI-007 which correctly recorded status='failed' with reason text when their changes were discarded. WI-005 recorded success with a detailed summary of files/behaviour added, but no commit hash was ever captured, and the working tree reset performed when the later WI-006/WI-007 attempts failed (`git status` is clean at 'Build: scaffold backend') wiped out whatever WI-005 had actually written, with no safety net because there was nothing committed to restore.
Expected: A work item should only be marked 'done' once its changes are committed (non-null commit hash); if a later item's revert resets the tree, a 'done' predecessor's commit should survive or be re-applied.
Actual: WI-005 is 'done' with commit=null, so its entire deliverable was lost with no trace other than the free-text summary and stale dist/ artifacts. This is a process defect that lets completed work silently disappear and should be fixed before trusting any future 'done' status without a commit.
