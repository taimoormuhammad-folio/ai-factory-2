# Clarifications

Q: Guest vs signed-in cart: on login, merge guest cart into account cart or keep separate—preferred customer experience?
A: Merge the guest cart into the signed-in account cart on login when both have items—combine quantities for matching products and keep distinct line items otherwise. That is what shoppers expect and it avoids losing items they already picked. If merging is technically heavy for this release, replace the account cart with the guest cart rather than keeping two separate carts.
Q: Wishlist persistence: local-only for guests and API for signed-in users, or API for both when authenticated?
A: Guests keep a local-only wishlist on the device. Signed-in customers use API-backed wishlist so favorites follow them across sessions and devices. On register or login, offer to import the local guest wishlist into the account wishlist once.
Q: Geography and fulfillment: which countries/regions we ship to, shipping rates, and tax display rules for checkout?
A: Ship to the United States only for Release 2 (contiguous states is fine for the demo). Show a flat standard shipping rate (for example $5.99) and free shipping over a seeded threshold (for example $75). Display sales tax as an estimated line at checkout using a simple fixed rate on the order subtotal after discounts (for example 8%) with copy that the final tax may vary—no complex jurisdiction engine in this pass.
Q: Coupon rules: single code per order, stacking, expiry, minimum order value, and category/product exclusions in seed promos?
A: One coupon code per order—no stacking. Seed promos must support expiry dates, minimum order value, and optional exclusions (specific categories or products). Percent-off and fixed-amount-off codes are both fine. Invalid, expired, below-minimum, or excluded-item orders should show a clear error at checkout.
Q: Order tracking detail: status labels only vs carrier name and tracking number in Release 2?
A: Show the status progression (processing → shipped → delivered) on every order. When an order is shipped or delivered, also show carrier name and a tracking number (seeded demo values are fine). Processing-only orders can omit tracking until shipped.
Q: Account policy: minimum password rules, email verification required or optional, and social login (Google/Apple) in a future release or now?
A: Passwords: minimum 8 characters with at least one letter and one number. Email verification is optional for Release 2—accounts can shop immediately after register; show a non-blocking “verify your email” stub if you implement verification at all. Google and Apple sign-in are out of scope for Release 2; plan them for a later release.
Q: Checkout payments: Stripe PaymentIntents in test mode with server-created intent, app confirmation, and webhook marking orders paid—or mock payment / PaymentIntent stub only with no Stripe integration?
A: Use a mock payment / PaymentIntent stub only—no Stripe keys, no live or test Stripe integration, and no webhooks in this release. The app should complete checkout with a demo “pay now” step and the server should mark the order placed (and paid for demo purposes) without touching a real processor.
Q: Support channel: email, phone, web form, or chat—and expected response-time messaging on the support screen?
A: Primary channel: support email (for example support@shopease-demo.com) with a simple in-app form that sends or simulates a message. No live chat or phone for Release 2. On the support screen, state that we aim to respond within one to two business days.
Q: Password reset stub: email link simulation only vs in-app flow with mock backend?
A: Provide an in-app password reset flow (enter email → confirmation message → enter new password) backed by a mock API—no real email delivery required. Optionally mention that a production build would email a link; for the demo, in-app with mock backend is enough.
Q: Product catalog scope: which categories, brands, and inventory rules define the seed data for filters and availability?
A: Seed a compact but realistic catalog: categories such as Clothing, Electronics, Home & Kitchen, Beauty, and Sports & Outdoors; multiple brands per category (roughly 8–12 brands total) so brand filters are meaningful; each product with price, category, brand, and availability (in stock, low stock, out of stock) so availability filters work. Include enough SKUs (on the order of 50–100 products) to make search, sort, and filters credible in demos.
Q: Minimal read-only admin API: worth doing in this pass if time allows, and which read-only views (orders, products, coupons) matter most?
A: Worth doing only if it does not jeopardize shopper features and tests. Priority order: read-only orders list/detail (for demo follow-up), then read-only products, then read-only coupons. Skip admin UI entirely; a minimal API or JSON endpoint is enough for internal demo validation.
Q: Legal and compliance: privacy policy, terms of sale, and cookie/consent copy for demo vs pilot users—required in-app screens or deferred?
A: Include lightweight in-app screens for Privacy Policy and Terms of Sale with placeholder/demo copy linked from registration, checkout, and account/settings—not deferred. Full legal review and production-ready consent flows can wait until pilot; for Release 2, visible links and static screens satisfy demo and early pilot expectations.
