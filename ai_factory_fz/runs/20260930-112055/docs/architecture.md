# Architecture

beauty-mvp phase 1 is a Flutter-only demo app for iOS and Android built from one codebase. It has three screens: Product List with category filters, Product Detail and Cart. It has no running backend, no accounts, no network calls and no payments. The catalog of about 24 products is a bundled JSON fixture (assets/mock/catalog.json). Each record conforms exactly to the Product schema of the OpenAPI 3.1 contract in this document. The app reads the fixture through a CatalogRepository interface in lib/features/catalog/data. Phase 1 ships MockCatalogRepository, which parses the fixture with the models generated from the contract (packages/api_client, dart-dio, json_serializable) and maps them to domain entities. A later phase adds ApiCatalogRepository, which calls the same generated client against the NestJS catalog module. That swap is one Riverpod provider override and does not change the domain or presentation layers. The cart is a single anonymous in-memory Riverpod Notifier per app session. It is never persisted and is not part of the API. This intentionally overrides the signed-in-cart convention, as the PRD states. Money is integer minor units (cents) with ISO 4217 currency USD everywhere, including the fixture, domain, cart arithmetic and contract. It is formatted to dollars only at display time. The contract covers only what the stories need: GET /categories, GET /products (category filter plus pagination) and GET /products/{productId}. It also includes the infrastructure health check. The Prisma schema models only the catalog (Category, Product, ProductImage, ProductVariant) so that the future backend can serve this contract. Users, carts, orders and payments are deferred to the phase that brings accounts and checkout. Checkout in the demo is a placeholder that shows 'Checkout is coming soon. This is a demo.' and triggers no navigation, state change or network call.

## Components
- **beauty_mvp Flutter app** (Flutter 3.x (Dart 3), Riverpod (Notifier/AsyncNotifier), go_router, freezed for domain entities, cached_network_image-compatible image widget with asset fallback, intl-free integer money formatter): The single mobile codebase for iOS and Android. It renders the Product List (with the All plus four category filters), Product Detail (with size or shade selector where applicable) and Cart (with quantity controls, Remove, subtotal and the placeholder Checkout). It owns in-memory cart state and brand theming, and handles loading, empty and error states on every screen.
- **Mock catalog data source** (assets/mock/catalog.json plus assets/images/products/*, loaded via rootBundle; validated in CI by a Dart test that parses every record with the generated models and asserts domain invariants): A bundled JSON fixture with about 24 products (about 6 per category) and the 4 categories. Each product record conforms to the OpenAPI Product schema and each category record to the Category schema. It holds prices as integer cents with currency USD, and variants as size or shade options with an optional default. Product images are bundled assets referenced by relative uri-reference. Neutral placeholders are used when a product has no images. The client supplies all content and holds the rights to it.
- **Generated API client package** (packages/api_client generated with openapi-generator dart-dio (serializationLibrary=json_serializable); regenerated from openapi.yaml, never edited by hand): The models (and future HTTP operations) generated from openapi.yaml. In phase 1 only the models are used, to parse the fixture, which guarantees the mock data matches the contract. In a later phase the generated CatalogApi and HealthApi replace the mock repository. No hand-written endpoints are allowed.
- **Core layer (lib/core)** (Dart, Flutter ThemeData/ThemeExtension, go_router): Shared code. This covers theme built from design tokens (colors, typography, spacing, radii, touch-target minimums), the go_router configuration (one route per screen), the money formatter (integer cents to '$24.00'), and shared widgets (ProductImage with placeholder, CartIconBadge, QuantityStepper, AsyncStateView for loading, empty and error states). It also holds the network placeholder, which is unused in phase 1.
- **OpenAPI contract** (OpenAPI 3.1 YAML at repo root (openapi.yaml), linted with Redocly/Spectral in CI): The source of truth for catalog data shapes, now (fixture) and later (backend). It defines the health, categories, products list and product detail operations, the shared Error schema, pagination, bearer auth scheme (reserved for future authenticated operations) and Money as integer minor units.
- **Future catalog backend (not built in phase 1)** (NestJS, Prisma ORM, PostgreSQL 16, @nestjs/swagger, Docker/docker-compose (staging), GitHub Actions): A later phase implements the contract with the NestJS catalog and health modules backed by PostgreSQL through Prisma, and swaps the app to the ApiCatalogRepository. It is documented here so phase 1 decisions do not block it.
- **CI pipeline** (GitHub Actions (macOS runner for iOS build and tests, Linux runner for Android and analysis)): Runs on every push. It lints the OpenAPI document, regenerates api_client and fails if the regenerated output differs from what is committed, then runs flutter analyze, the fixture validation test, widget tests per screen and the integration_test main journey. It builds iOS and Android debug artifacts for the demo devices.

## Backend modules
### health (future phase; contract defined now)
Reports liveness and database reachability. It returns 200 when PostgreSQL answers a trivial query and 503 with the shared Error schema otherwise. It is public and not counted in the operation limit.
Entities: 

- `GET /api/v1/health`

### catalog (future phase; contract defined now, served by bundled fixture in phase 1)
Read-only public catalog. It lists categories, lists active products with an optional category filter and page/pageSize pagination (returning items and total), and returns a single product with its images and size or shade options. Controllers stay thin. CatalogService maps Prisma rows to the OpenAPI schemas exactly, including Money as integer minor units and variantType none/size/shade. Unknown or inactive product ids return 404 with the shared Error schema.
Entities: Category, Product, ProductImage, ProductVariant

- `GET /api/v1/categories`
- `GET /api/v1/products`
- `GET /api/v1/products/{productId}`

## Mobile app features
- catalog (lib/features/catalog): screens Product List (route '/', name productList): a scrollable 2-column grid of product cards (image or neutral placeholder, name, brand, price as $x.xx). A horizontal filter bar offers exactly 'All' plus Skincare, Makeup, Haircare and Fragrance. The selected filter is highlighted, and tapping the active filter again clears it back to All. There is no search or sort. A cart icon with an item-count badge sits in the app bar. The grid uses a PageStorageKey so the scroll position is kept when returning from detail. The screen has loading, empty ('No products in this category') and error (retry) states., Product Detail (route '/products/:productId', name productDetail, pushed on top of the list with context.push so back returns to the same scroll position): shows the larger image carousel (placeholder if none), name, brand, price, description, and a shade selector (variantType shade) or size selector (variantType size), with exactly one option selectable. It shows no selector when variantType is none. The Add to Cart button adds quantity 1 and shows a snackbar confirmation. If a selector is present and no option is selected (and no default was preselected), the item is not added and a 'Please choose a size' / 'Please choose a shade' message is shown. The screen has loading, not-found (unknown id, with a back-to-list action) and error states. (state: Riverpod. catalogRepositoryProvider (Provider<CatalogRepository>) defaults to MockCatalogRepository, and tests and future phases override it. catalogProvider (AsyncNotifier<List<Product>>) loads the full catalog once (equivalent to listProducts with page=1, pageSize=100) and caches it for the session. categoriesProvider (FutureProvider<List<Category>>) supplies the categories. selectedCategoryProvider (Notifier<CategorySlug?>, null = All) exposes select(slug), which toggles to null when slug is already active. filteredProductsProvider (Provider<AsyncValue<List<Product>>>) filters in memory with no I/O, so it updates instantly. productDetailProvider (FutureProvider.family<Product?, String>) resolves by id from the catalog. selectedVariantProvider (AutoDispose Notifier.family<String?, String> keyed by productId) is initialised to the id of the variant with isDefault=true, or null when there is none. Domain entities are freezed classes (Product, ProductVariant, Category, Money, ProductImage) mapped from the generated api_client models in the data layer, so presentation never depends on generated types.)
- cart (lib/features/cart): screens Cart (route '/cart', name cart, reachable from the cart icon on every screen): each line shows image, name, brand, chosen size or shade label (if any), unit price, quantity stepper and line total, with a Remove action. The decrease control is disabled at quantity 1 and increase is disabled at 99. The subtotal is shown in US dollars, and a Checkout button below the subtotal shows a 'Checkout is coming soon. This is a demo.' snackbar/dialog and stays on the Cart screen with contents unchanged. The empty state shows a message and a 'Browse products' action that goes to '/', with no Checkout button shown. All controls are at least 48dp. (state: Riverpod. cartProvider (Notifier<CartState>) holds an immutable list of CartLine {lineKey, productId, productName, brand, imageUrl?, variantId?, variantLabel?, variantType, unitPrice: Money, quantity}. lineKey is productId + ':' + (variantId ?? 'none'). Methods: add(product, variant?) increments quantity if lineKey exists (capped at 99) or appends a new line with quantity 1; increment(lineKey) caps at 99; decrement(lineKey) is a no-op at 1; remove(lineKey). The state lives in memory only, is not persisted and resets on app relaunch. Derived providers are cartItemCountProvider (sum of quantities, used by the badge) and cartSubtotalProvider (Money). The subtotal is computed as the integer sum of unitPrice.amountMinor * quantity, for example 1999*3 + 850 = 6847 -> $68.47. Checkout is a pure UI action in the presentation layer with no provider mutation, route change or I/O. All operations are synchronous, which meets the 300 ms update budget.)

## Data model
1) Money: every price is an integer number of minor units (cents) plus an ISO 4217 code. In the contract this is the Money object {amountMinor: integer, currency: 'USD'}. In Prisma it is Product.priceAmountMinor (Int) plus Product.currency (Char(3), default 'USD'). Floats are never used. The Dart formatter uses integer arithmetic (dollars = cents ~/ 100, cents % 100 padded to 2 digits, thousands separators) to render '$24.00'. Line totals and subtotal are integer multiplications and sums; Dart int is 64-bit on mobile, so there is no overflow at demo scale (99 x max price). 2) Categories: exactly four slugs (skincare, makeup, haircare, fragrance), with display name and sortOrder. The 'All' option is a UI concept (null filter), not a category. 3) Variants: Product.variantType is none, size or shade. Makeup products use shade, skincare and haircare use size, and fragrance uses size or none per client data. ProductVariant has label (e.g. '50 ml', 'Rose Nude'), sortOrder, isDefault (at most one per product) and optional swatchHex for shade swatches. Per the PRD, variants carry no price, image or stock. Invariant: variantType none if and only if the variants list is empty. The fixture validation test and, in the future, a DB check/service validation enforce this. The stock-per-variant project convention is deliberately deferred because stock is out of scope. A later migration adds a stock quantity column to product_variants when checkout arrives. 4) Images: ProductImage rows are ordered by sortOrder. ProductSummary.image is the first image and is omitted when the product has none, in which case the app shows a neutral placeholder. url is a uri-reference. In phase 1 it is a relative path resolved against the app asset bundle (e.g. 'assets/images/products/serum-01.jpg'); in future phases it is an absolute https CDN URL. altText is required for accessibility semantic labels. 5) Identifiers: product, variant and category ids are UUIDs, and the fixture uses fixed UUIDs so tests are deterministic. 6) Cart: not persisted and not modeled in the database or API for this demo. CartLine copies productName, brand and unitPrice at add time. This mirrors the order-line snapshot convention and makes the later move to a server cart and order lines straightforward. 7) Pagination: list operations accept page (>=1, default 1) and pageSize (1..100, default 20) and return {items, total, page, pageSize}. The demo loads all 24 products in one page (pageSize=100). 8) Deferred entities: User, Address, Cart, CartItem, Order, OrderItem and Payment are intentionally not in the Prisma schema. They arrive with accounts and checkout, following the project order status flow and Stripe PaymentIntent conventions. 9) Database-level guards added in the future initial migration via raw SQL: CHECK (price_amount_minor >= 0), CHECK (currency ~ '^[A-Z]{3}$'), and a partial unique index on product_variants(product_id) WHERE is_default.

## Security
- No personal data: the demo collects, stores and transmits no personal data. It has no accounts, sign-in, passwords, analytics SDKs, crash reporters that send PII, or payment data. flutter_secure_storage is not needed in phase 1 because there are no tokens.
- No card data anywhere: Checkout is a UI-only placeholder. A widget test asserts that tapping Checkout performs no navigation and no cart mutation, and the integration test runs with no network client registered. No Stripe SDK is included in phase 1.
- No network at runtime: the catalog and images are bundled assets. The app makes no HTTP calls, so the attack surface is limited to the app binary. The dio/api_client dependency is used for models only.
- Android network security: release builds are https-only (cleartextTrafficPermitted=false, the platform default). A debug-only network_security_config in android/app/src/debug permits cleartext solely for 10.0.2.2, so debug builds can reach local staging in future phases. iOS keeps App Transport Security defaults with no arbitrary loads.
- Content rights: only client-owned or licensed images, descriptions, brand names and prices go into the fixture. Placeholders are neutral assets created by the team. The fixture carries a README noting provenance.
- Supply chain: pin Flutter SDK and package versions (pubspec.lock committed), run flutter pub outdated/audit in CI, and keep dependencies to the listed boring stack.
- No secrets in code or repo: phase 1 needs no secrets. Future base URLs and keys come from --dart-define / environment and are never committed.
- Future API (contract-level): catalog operations are public read-only (security: []), with the bearerAuth JWT scheme reserved for future authenticated operations (15-minute access tokens plus refresh tokens). Query parameters are validated with class-validator: page >= 1, pageSize 1..100, category restricted to the enum, productId must be a UUID. Errors always use {statusCode, error, message} and never leak stack traces. Rate limiting applies to public endpoints. Helmet and CORS are locked to known origins. Prisma parameterised queries prevent SQL injection.
- Future account deletion and password hashing (argon2/bcrypt) are required when accounts arrive. They are not applicable in phase 1.

## Architecture decisions
### ADR-001: Phase 1 is Flutter-only with a bundled mock catalog behind a repository interface
**Context:** The PRD excludes backend services, accounts, checkout and network connectivity, and needs a demo-ready build in 3-4 weeks on a limited budget. The demo runs on physical phones where network conditions are unknown. The project target stack (NestJS, PostgreSQL, Stripe) is for later phases.

**Decision:** No backend is built or deployed in phase 1. The app loads assets/mock/catalog.json and bundled images through CatalogRepository, whose default implementation is MockCatalogRepository, exposed via catalogRepositoryProvider. The repository interface mirrors the contract operations: listCategories, listProducts(category?, page, pageSize) and getProduct(id). Filtering for the demo happens in memory on the fully loaded catalog.

**Consequences:** The demo cannot fail because of connectivity or server issues, and Product List easily meets the 2-second load target. There is no infrastructure cost or operational burden. Catalog changes require a new app build, which is acceptable for a demo. Moving to a real backend means implementing ApiCatalogRepository and overriding one provider; the domain and presentation layers are untouched. The Android-first delivery preference is overridden by the PRD's iOS priority for the demo, but both platforms are built and tested in CI.

### ADR-002: Contract-first OpenAPI now, with the mock fixture validated against generated models
**Context:** Developers must build against an exact contract without guessing. The project convention forbids hand-written HTTP endpoints in the app. If the mock data drifts from the eventual API shape, the later backend integration becomes a rewrite.

**Decision:** Write openapi.yaml (OpenAPI 3.1) now, covering health, listCategories, listProducts and getProduct. Generate packages/api_client with dart-dio (json_serializable) and use its models to parse the fixture. A CI test parses every fixture record with the generated models and asserts invariants: price >= 0, currency USD, variantType none if and only if there are no variants, at most one default variant, and every image has altText. Cart and checkout are not in the contract.

**Consequences:** The fixture is guaranteed to match the future API byte-for-byte in shape. The generated client is ready for the backend phase. The app depends on the generated package, so contract changes require regeneration, which CI enforces with a diff check. The contract stays small (3 operations plus health), well within the 10-operation limit.

### ADR-003: Money as integer minor units with ISO 4217 code; display-only formatting
**Context:** The PRD and project rules forbid floats for prices. The acceptance test requires $19.99 x 3 + $8.50 = $68.47 exactly.

**Decision:** Money is {amountMinor: int, currency: 'USD'} in the contract, fixture, domain and cart. It is Int plus Char(3) in Prisma. Line totals and subtotals are integer arithmetic. A single formatter in lib/core formats cents to '$x,xxx.xx' using integer division and remainder, never converting to double.

**Consequences:** There are no rounding errors, and the subtotal acceptance test is deterministic. Multi-currency later needs only formatter changes, because the currency code is already carried. Every developer must use the shared formatter; a lint/test guards against double-based price formatting.

### ADR-004: Single anonymous in-memory cart per session (overrides the signed-in cart convention)
**Context:** The project convention says a cart belongs to a signed-in user. The PRD explicitly excludes accounts and cart persistence and requires the cart to reset on relaunch.

**Decision:** The cart is a Riverpod Notifier<CartState> held only in memory. Lines are keyed by productId plus variantId, so the same product and variant increments quantity and a different variant creates a new line. Quantity is bounded to 1..99. Lines snapshot name, brand, image and unit price at add time. There is no cart API and no database table in this phase.

**Consequences:** Cart actions are synchronous and well under 300 ms, and there is nothing to secure or migrate. The cart is lost on app close, as required. When accounts arrive, a server-side cart (Cart and CartItem tables plus endpoints) replaces this Notifier's storage while keeping the same public methods. The snapshot fields map directly to order-line snapshot rules.

### ADR-005: Variants as simple size or shade options without price, image or stock
**Context:** The PRD scopes variants to a single selectable size (skincare, haircare, optionally fragrance) or shade (makeup) that is only recorded on the cart line. Per-variant price, image and stock are out of scope, although the project convention tracks stock per variant.

**Decision:** Product.variantType (none|size|shade) determines which selector is shown. ProductVariant has id, label, sortOrder, isDefault and optional swatchHex. Price lives on Product only. The first/default option is preselected when isDefault is true; otherwise Add to Cart requires an explicit choice. Stock columns are deferred.

**Consequences:** The UI logic is trivial and fully data-driven, and the client can decide per product whether to preselect a default by editing the fixture, which resolves the PRD's open question without code changes. Adding per-variant stock or price later is an additive migration plus optional contract fields.

### ADR-006: go_router with detail pushed over list to preserve scroll; Riverpod for all state
**Context:** US-001 requires back from Product Detail to return to the list at the same scroll position. The project mandates go_router with one route per screen and Riverpod Notifier/AsyncNotifier.

**Decision:** Routes are '/' (productList), '/products/:productId' (productDetail) and '/cart' (cart). Product cards navigate with context.push so the list stays mounted beneath. The grid uses a PageStorageKey, and filter state lives in selectedCategoryProvider, so both survive navigation.

**Consequences:** Scroll and filter state are preserved without extra code. Deep links to a product id work for future marketing needs, and unknown ids render the not-found state. Widget and integration tests can drive navigation by route name.

The API contract is in `openapi.yaml`; the data model is in `schema.prisma`.
