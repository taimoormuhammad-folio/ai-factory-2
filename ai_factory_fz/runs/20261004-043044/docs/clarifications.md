# Clarifications

Q: For Release 2 demo checkout, should orders be paid via Stripe PaymentIntents in test mode with client confirmation and a webhook marking the order paid (per platform payment rules), or is a mock payment flow with no Stripe integration acceptable as the sole path?
A: For Release 2 demo, a mock payment flow with no Stripe integration is acceptable as the sole path. We still want the experience to follow a secure pattern—no raw card storage, clear pay step, and order marked paid only after successful mock confirmation—so we can swap in a real gateway later. Stripe PaymentIntents in test mode with webhooks is a good follow-on for production readiness, not a requirement to call Release 2 done.
Q: For Release 2, do all shoppers—including trade/electrician buyers—use the same VAT-inclusive B2C price list, or do you require trade account types, ex-VAT display, or separate pricing that affects catalog, cart, and checkout?
A: For Release 2, everyone—including trade and electrician buyers—uses the same VAT-inclusive B2C price list shown in the catalog, cart, and checkout. We are not introducing trade account types, ex-VAT display, or separate trade pricing in this release; that stays on the backlog until we have VAT/invoicing and trade discount rules signed off.
Q: For FR-12 Wishlist, is the scope registered users only (API-backed), or must guest users also save favorites (e.g. local-only) before sign-up?
A: Release 2 wishlist is registered users only, API-backed and synced when signed in. Guests can browse and buy without a wishlist; if they want saved favorites, they register or log in. Local-only guest wishlists are out of scope for this pass unless we have spare capacity—nice for conversion later, not required for the demo.
Q: For FR-13 checkout shipping, should MVP/Release 2 use a single simplified UK domestic rule (e.g. one flat rate or free over a threshold), or do you need multiple zones, carriers, or weight-based rules defined now?
A: Use a single simplified UK domestic shipping rule for MVP and Release 2—for example one standard flat rate for mainland UK, with free delivery over a stated order threshold (e.g. £75), and copy that makes clear it is standard domestic only. We do not need multiple zones, carrier choice, or weight-based tables in this release; those are production decisions once we pick carriers and surcharges for oversized or fragile lighting.
Q: For order lifecycle beyond tracking display, which customer-initiated actions are in scope for Release 2: cancel while pending payment, cancel before fulfillment, return requests, or refunds—or are cancelled/refunded statuses staff/API-only with no in-app customer flow?
A: For Release 2, customers see order history and status progression (processing → shipped → delivered) and any seeded shipment info—we are not building in-app cancel, return, or refund flows. Cancelled and refunded statuses may exist in the API or back office for demo/staff use, but there is no shopper self-service for those actions in the app this pass. Returns, refunds, and warranty handling stay policy and FAQ copy plus support contact until a later release.
Q: For FR-19 promotions at checkout, should coupon codes work for guest checkout as well as signed-in users, and what stacking rules apply (one code per order, minimum order value, category/SKU restrictions, stacking with sale or variant prices)?
A: Yes—coupon codes must work for both guest checkout and signed-in users, using the same seeded promos. Rules for Release 2: one coupon code per order; minimum order value applies where the seed defines it; category or SKU restrictions apply only when the promo seed specifies them. The coupon applies to the order subtotal after line-item sale or variant prices are already reflected (one discount layer from the code on top of displayed prices); codes do not stack with each other, and we are not modelling trade-rate stacking in Release 2 because all shoppers share one price list.
